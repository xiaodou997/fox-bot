## 1. 已确定的目标与约束

| 编号 | 基线 |
| --- | --- |
| D-01 | 产品覆盖微信、QQ、飞书、X 私信；首批平台组合严格以适配矩阵为准，不自动扩成所有交叉组合。 |
| D-02 | Android 直接分发签名 APK，不以 Google Play 上架为前提；仍遵守操作系统权限与运行限制。 |
| D-03 | 同时支持人工辅助、自动建议、全自动回复；用户授权指定账号和会话范围后，全自动模式不逐条要求确认。 |
| D-04 | 软件获取与收发和 AI 处理分离；不绑定 Jev，不强制意图分类、评分或候选排序模型。 |
| D-05 | 支持普通大模型接口及已绑定知识库、业务规则的定制回复服务；定制服务默认不被客户端追加角色提示词。 |
| D-06 | 优先结构化读取，截图只在必要时使用；OCR 优先本地小模型或系统引擎，不以通用视觉大模型作为基础依赖。 |
| D-07 | 当前会话闭环与多会话值守分别实现、分别验收；自动发送是 FoxBot 新增能力，不能继承上游的“填入”作为完成证据。 |
| D-08 | 会话不确定、人工接管、凭据失效或发送结果未知时，暂停相应执行；停止错误动作不等于把全自动退回逐条审批。 |

上述是产品范围。本文件后续的技术分工、字段和阶段安排是本次采用的工程工作基线，允许通过有理由、有影响说明的文档变更调整，不表示所有实现细节已由用户逐项确认。

## 2. 非目标与分期边界

首批做普通客户端已有账号和授权会话，不要求切换为企业账号。官方接口仅作为可选通道，不是交付前提。

一期主要收发文字。图片、语音、附件、引用等必须保留内容类型与解析状态，不能悄悄丢弃后宣称上下文完整；自动转写、图片理解和文件发送后置。

不做任意桌面任务规划、群发营销、联系人批量拉取、全部历史扫描、转账支付或任意工具执行。不 hook、不注入、不读取其他应用数据库或进程内存，不伪装系统服务身份，不绕过受保护窗口或权限边界。参考代码存在的实验行为不默认迁入。

Android 微信为独立能力探测专项；iOS 的辅助导入或管理端后置，不承诺普通 iOS 应用可以在本机控制任意聊天软件。平台事实与限制的依据见来源审计。

## 3. 运行模式、授权与接管

| 模式 | 触发 | 输出与动作 |
| --- | --- | --- |
| ASSISTED | 用户选择内容、输入要求或点击生成 | 候选预览；用户选择复制、回填或发送。 |
| AUTO_SUGGEST | 授权范围内的新消息 | 自动生成候选，不自动写入和发送。 |
| AUTO_REPLY | 授权范围内的新消息 | 自动调用回复服务；通过执行校验后自动发送。 |

新配置默认暂停。启用 AUTO_REPLY 时明确展示账号绑定、允许的会话、群聊触发规则、AI 服务目的地、是否允许切换窗口及运行设备类型。正常消息无需逐条确认。

授权粒度为设备绑定、应用实例/账号、会话或显式配置的会话范围，不能仅以应用名或联系人标题作为授权依据。未在首批范围内的应用不会被静默扫描。

日常共用设备以用户操作优先；用户编辑、输入法组字、手动发送或主动改变目标会话时，暂停冲突任务。专用值守设备可在明确授权范围内导航，但仍保护未归属 FoxBot 的草稿。恢复应有明确入口，不能凭一个短定时器偷偷重新夺回输入。

锁屏、权限撤销、应用退出、账号切换和设备休眠需要明确状态。GUI 通道停止不安全动作；通知/API 通道能否继续由各自能力与策略决定，不从“后台进程存在”推导为可收发。

## 4. 逻辑架构

```text
平台驱动：窗口 / 通知 / AX / UIA / Accessibility / 截图 / OCR / 输入
                         ↓
应用适配器：发现会话、提取消息、定位编辑器、导航、回填、发送、验证
                         ↓
运行核心：身份与权限 → 消息归一 → 去重与合并 → 会话队列 → 版本与取消
                         ↓
回复服务适配器：通用模型 / 有状态业务服务 / 无状态业务服务 / 测试桩
                         ↓
运行核心：结果校验 → 持久化发件箱 → 获取执行权 → 目标复核
                         ↓
应用适配器：回填 / 发送 / 读取效果 → 回执 → 恢复与对账
```

### 4.1 职责边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| Platform Driver | 操作系统权限、窗口和坐标、原生控件、截图、OCR 推理、原子输入动作 | 业务提示词、联系人知识库、凭文本猜测发送对象 |
| App Adapter | 应用与版本识别、会话及消息解析、能力探测、导航、应用专属写入和发送验证 | 决定业务回答、不受限的跨应用规划 |
| Runtime | 身份、权限、事件、队列、并发、持久化、过期检查、执行策略、恢复 | 推断客户意图、补写缺失的 OCR 正文 |
| Reply Provider | 按配置的协议提交文本与允许的上下文，接收回复/不回复/转人工 | 授予设备权限、选择原生窗口、修改本地会话路由 |
| UI / Diagnostics | 配置、预览、暂停/接管、任务与错误解释、脱敏诊断 | 用展示中的临时状态代替持久化执行事实 |

逻辑分层不要求部署成微服务。一期核心可作为进程内库；会阻塞的采集、原生调用或 OCR 应采用有超时与恢复边界的线程/辅助进程。测试桩必须可以替代平台驱动和回复服务。

### 4.2 能力不是一个布尔值

每个适配器分别报告 discover、identify、read、route_group、draft_read、fill、send、verify、navigate、recover 等能力，详见矩阵。返回值应包含可用性、前提、证据、失败原因及下一步，而不是统一返回 success=true。

能读不代表能填，能填不代表能发送；触发发送不代表送达。未知、权限不足、不支持和空内容必须是不同状态。

## 5. 核心数据契约草案

内部 ID 必须稳定且不包含聊天正文；具体 ID 编码在实现阶段确定。下面是语义要求，不是已发布的序列化 ABI。

| 对象 | 必要语义 |
| --- | --- |
| AccountBinding | 本地 device_id、app_instance、account_binding_id；可观察的账号证据与 identity_epoch；账号不可辨认时要求显式绑定，发生不确定变化时失效。 |
| ConversationKey | account_binding_id、适配器确认的会话标识或局部会话绑定；标题只作展示。弱证据不能自动合并同名联系人。 |
| Observation | observation_id、采集时间、应用/窗口证据、布局版本、来源、可见范围与完整性、OCR/解析器版本。原生句柄是短期定位信息，不是跨重启身份。 |
| MessageEvent | event_id、ConversationKey、来源事件引用、方向 me/other/unknown、sender_id/显示名、正文与类型、mention/reply_to、顺序证据、解析完整性。来源缺少时间或 ID 时允许为空，不伪造。 |
| SessionRevision | 消息、身份、账号、配置与人工操作变更的版本；用于取消和失效校验。与窗口布局版本分别记录。 |
| ReplyTask | request_id、输入事件集合、观察版本、机器人/服务配置版本、上下文归属、取消状态、预算及队列状态。 |
| ReplyResult | reply/no_reply/handoff、完整文本或交接原因、可信服务返回的会话引用；发送目标仍由本地任务绑定。 |
| OutboundAction | action_id、输入事件集合、目标绑定、待发文本、幂等键、持久化阶段、发送通道、效果证据与未知状态。 |
| Receipt | 操作是否调用、通道是否接受、是否观察到己方输出、是否有平台送达/已读证据，各项独立记录。 |

来源和置信信息必须与正文一起传到策略层。不同 OCR 引擎的原始 confidence 不可不经校准直接相互比较；没有置信分数不能伪造为 1.0。

### 5.1 初始化与新消息

启动或恢复时建立当前会话观察基线。屏幕已有消息可作为上下文，但默认不是待回复的新任务，不批量补回旧消息。

开启后新增消息、重复通知、通知更新、OCR 重复帧、滚动重现和历史回放必须区分。发现缺口要显式标记，不承诺纯 GUI 通道可读取未显示的全部消息或恢复全部离线消息。

文字哈希只可作为局部证据，不能作为永久消息 ID。同一人连续发送两个“好的”必须允许成为两条消息；同一消息由通知和 OCR 重复观察应尽量合并，证据不足时保留歧义而非制造确定事实。

### 5.2 群聊与内容完整性

私聊默认处理已授权的新消息；群聊默认只处理可以明确确认提及当前账号的消息，可按群启用全部消息处理。识别不到真实提及，不把普通文本“@名字”当成可靠 mention。

保留发言人、引用对象与轮次；不能统一压成“对方”。发言人或目标不确定的任务不得直接发送。图片/语音等未解析内容用类型和 incomplete 标记交给服务；普通文本通道不得隐瞒这些缺口。

## 6. 回复服务协议

### 6.1 两类接入

通用模型模式由 FoxBot 按用户配置组装提示词和有限上下文。协议、Base URL、模型、凭据、流式输出、结构化结果等能力分别配置，不能把所有服务都假定为同一个协议。

定制业务服务模式默认原样传递允许的消息数据，不强加角色、不重复实现知识库、不强制多候选、不增加 Jev 或第二个判断模型。仅返回字符串的既有服务可由确定性的适配器包装为 reply。

下面为拟议 envelope；并非要求所有现有服务照此改造。字段映射由受信任适配代码完成，凭据仅存在本地安全配置。

```json
{
  "schema_version": "0.1",
  "request_id": "req_example_001",
  "idempotency_key": "turn_example_001",
  "conversation_ref": "opaque_local_conversation",
  "session_revision": 7,
  "provider_profile_version": 2,
  "context_mode": "service_managed",
  "server_conversation_id": null,
  "input_events": [
    {
      "event_id": "evt_example_001",
      "sender_ref": "opaque_sender",
      "direction": "other",
      "type": "text",
      "text": "这个产品如何安装？"
    }
  ],
  "context_complete": true
}
```

```json
{
  "schema_version": "0.1",
  "request_id": "req_example_001",
  "in_reply_to": ["evt_example_001"],
  "result": "reply",
  "message": {"type": "text", "text": "请按以下步骤安装……"},
  "server_conversation_id": "server_example_001"
}
```

服务也可返回 no_reply 或 handoff；这只是业务结果协议，不要求运行额外意图分类。模型正文中的 JSON、命令或“换个联系人发送”等文本均不能改变可信 envelope 的路由。

### 6.2 会话归属与结果约束

| 场景 | 规则 |
| --- | --- |
| client_managed | 客户端发送有限上下文，明确是否含未解析内容与已实际发出的回复。 |
| service_managed | 映射本地账号＋会话＋服务配置到服务端会话，按服务约定传增量；不能每次重复追加全量历史。 |
| 服务/模型/知识库配置变化 | 增加配置版本，隔离或重建服务端会话；旧任务不得使用新凭据或新目的地继续执行。 |
| 生成完成但尚未发送 | 不能记录成客户已经看到的回复；若服务生成时自动写入历史，适配器必须提供草稿/提交/取消或分支对账策略。 |
| 服务没有幂等/对账能力 | 明确标记限制；对可能已入账的超时请求禁止假定重试无副作用。有状态服务在故障恢复验收前不能宣称可靠全自动。 |
| 输出截断、取消、畸形或超长 | 不发送半截流式结果，不静默截掉业务语义；转为受控错误、重生成或交接。 |
| 服务故障 | 按配置有限重试；不擅自换模型供应商、知识库或发送另一段兜底业务回答。 |

客户端取消请求不等于服务端停止执行。晚到结果必须通过 request_id、会话版本与配置版本检查，失效结果不可回填或发送。

服务配置需声明重试、状态持久化、历史修正及回执接口能力。发送事实回传失败应进入独立对账队列，不因回执网络错误重新发送客户消息。

## 7. 调度与可靠发送

### 7.1 队列与并发

同一会话有序处理，短时间连续消息可合并但必须有最大等待。不同会话的模型调用可以限并发执行；一期同一设备所有 GUI 输入共享一个执行锁。

多个进程不能同时拥有同一设备上的自动执行权。跨设备一期采用显式指定的单一发送端，不宣称仅凭本地锁能够排除另一台设备重复发送；未配置唯一所有者的部署不进入全自动支持范围。

新消息在生成期间到来时，对尚未产生发送副作用的旧任务作失效/合并处理。任务进入可能已发送阶段后，必须先对账，不能把“取消”当作撤回已发生动作。

防止回复自身输出；为每会话设置自动连续回复次数、冷却、消息长度、队列深度和调用预算上限。超过限制明确暂停，不使用模仿真人的随机行为来规避平台检测。

### 7.2 状态与持久化边界

```text
OBSERVED → BASELINED（历史，仅上下文）
         → QUEUED → GENERATING → READY
                              → NO_REPLY / HANDOFF / STALE / ERROR

READY → PREPARED（待发任务已持久化）
      → EXECUTING（产生副作用前写入执行标记）
      → SUBMITTED（只证明已调用通道）
      → VERIFIED_OUTGOING（观察到匹配的己方输出）
      → UNKNOWN（无法确认是否发送，等待核对）
```

PREPARED/EXECUTING 的更新与本地任务领取须具备事务边界。进入 EXECUTING 后崩溃、超时或窗口丢失，恢复时按“可能已发生副作用”核对，不能默认重新开始。

平台 ACK、界面己方气泡、送达、已读是不同证据，不压成一个 success。VERIFIED_OUTGOING 不是对方已收到；对发送失败图标或不明确关联需继续区分。

GUI 通道不承诺 exactly-once。策略是尽量避免重复发送，同时把无法确认的任务显式交给核对；这可能延迟个别回复，不能宣称同时绝不重复、绝不漏发。

### 7.3 执行前后检查

发送前重新解析账号、会话、窗口、布局和编辑器；检查观察版本、输入事件、策略、草稿、输入法组字和人工接管状态。不得只复用生成开始时的坐标。

默认不覆盖/拼接用户已有草稿；属于本任务的写入也要在重新读取后才恢复。读取失败与空草稿不同。焦点改变后必须再次核对，写入返回 true 不能代替读回验证。

每个适配器定义自己的发送动作；公共核心不写死 Enter。截图坐标必须绑定捕获原点、缩放、窗口和布局版本。剪贴板作为可选降级时，不覆盖期间用户新复制的内容；不能保证安全读回时停止自动发送。

发送结果未知时不换通道盲目重发。核对未发现消息也不自动证明未发送，需要结合已验证的通道证据和配置处理。

## 8. OCR、资源与诊断

OCR 引擎负责文字和位置，适配器负责气泡、发言人、引用和顺序。系统树读取成功时不额外跑整屏 OCR；自绘应用可直接采用已验证的截图路线，不机械重试不存在的控件树。

| 平台 | 首轮工程候选 | 未冻结事项 |
| --- | --- | --- |
| Android | ML Kit 中文 bundled；可比较 ncnn＋轻量 PP-OCR | 版本、模型许可、ABI、真机性能与聊天准确率 |
| macOS | Apple Vision；必要时对比同一轻量 OCR 样本 | 系统版本、语言配置、模式与短数字识别策略 |
| Windows | 轻量 PP-OCR＋ONNX Runtime；RapidOCR 作参考/基准 | 权重、字典、预后处理一致性、原生桥接与包体 |

技术资料见来源审计。候选不等于已经引入依赖；本基线不承诺具体模型大小、内存、耗时或官方通用数据集准确率可以复用于聊天界面。

裁剪必要区域、事件优先、有限轮询、增量帧、背压和低频重新同步均应可配置。OCR 已忙时丢弃过期帧而非无限排队；引擎可按空闲状态卸载。禁止语言模型替原消息静默纠错，数字、金额、型号和否定词要保留原始识别证据。

诊断界面展示选用通道、观察内容、未解析类型、身份/布局置信情况、队列阶段及暂停原因。调试图默认仅内存；导出前脱敏、预览和显式确认。

## 9. 技术方向与数据保护

工作基线：共享 Rust 核心；桌面 Tauri＋Vue/TypeScript；Android Kotlin 原生服务与界面；macOS 与 Windows 使用平台原生桥接。Swift、Rust 原生绑定、FFI/UniFFI 的具体分工在平台探针后锁定，不为共享 UI 牺牲生命周期与权限正确性。

SQLite 保存最小运行日志、收件事件、发件箱与对账状态。聊天长期历史单独设置，默认不启用；运行账本不能因为关闭聊天历史而消失。待发敏感正文需受保护存储并有保留/清除策略；系统凭据库不可用时明确错误，不降级为仓库、日志或明文配置中的密钥。

AI 请求只发送配置允许的消息与上下文；默认不上传截图。普通聊天正文不是本地控制指令。端点、账号和服务配置由用户管理，回复不得改变它们。凭据、通知动作/令牌、完整提示词和聊天内容不得进入公开诊断。

版本发布按平台确定最低 OS、架构和支持应用版本，不照搬其他项目的系统下限。Android 的截图基线与 APK 权限引导、桌面签名与分发、升级回滚均需单独验收。APK 直装并不消除系统授权限制。

## 10. 阶段门禁

| 阶段 | 交付 | 通过边界 |
| --- | --- | --- |
| G0 文档基线 | 本基线、矩阵、清单、模板、来源与导航 | 文档一致且链接有效；不表示运行能力已实现。 |
| G1 模拟闭环 | Runtime、持久化、模拟消息/回复/发送通道 | 用故障注入证明隔离、去重、过期处理与恢复；不触碰真实聊天。 |
| G2 平台探针 | Android 与桌面采集、身份、草稿、OCR、通知能力报告 | 指定组合逐项记录真实能力；MC-WX current-session 只读链已有 Freeze 回执，但只读探测不证明可写/可发送。 |
| G3 当前会话自动收发 | 经授权测试会话的完整自动闭环 | 逐组合验证读、填、发、回执和异常；暂不声称多会话值守。 |
| G4 多会话值守 | 新消息发现、导航、队列、人工让权与多会话对账 | 不串会话、不补发旧历史、不因前台变化误写。 |
| G5 候选发布 | 平台包、升级、权限、资源与持续运行回执 | 按明确组合发布支持范围；未验收能力关闭或标记实验。 |

每个阶段使用[验收清单](../acceptance/ACCEPTANCE_CHECKLIST.md)的固定案例编号。G1 自动化通过不覆盖 G2–G5 真机门禁。代码合入与功能发布分别管理；允许合入未验收且默认关闭的实现，但不把它标记为 ACCEPTED。

## 11. 变更与待联调项

当前无需再确认目标软件、APK 分发、自动模式或 Jev 替换方向。待联调输入：目标应用/系统版本、主题与语言、设备和账号绑定方式、定制服务的脱敏请求/响应和状态语义。缺少这些输入不阻塞 G1，可用测试桩；会阻塞对应平台/服务的真实支持声明。

修改范围、自动发送授权边界、身份定义、消息语义或恢复策略时，必须说明动机、受影响矩阵行和回归案例；新增软件不能仅修改 README 支持表。模型、字典、适配规则更新均固定版本并允许回退，不把未经验证更新直接推给正在值守的执行端。
